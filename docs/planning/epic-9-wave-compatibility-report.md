## 4. Findings & reconciliations

### Finding 1 — `focusId` honoring is unowned (circular disclaim)  ·  severity: HIGH
9.1.1 delivers the `focusId` *mechanism* and says surfaces honor it "in 9.4.1." 9.4.1 says honoring is "C2's/9.1.1's obligation — this wave verifies and files gaps, it does not reimplement surfaces." **Neither implements the scroll-to-row + highlight inside `tasks`/`goals`/`email` surfaces.** The board (9.2.3) self-honors via `BoardRow.id`, so only the three list surfaces are affected — but for them, tool deep-links and `open_surface` would open the surface and silently fail to focus the row.
**Resolution (applied to C2):** `focusId` *honoring* is assigned to **Wave 9.4.1** as an implementation obligation, not a verification one — 9.4.1 adds minimal scroll-into-view + highlight to each C2-mapped list surface (`tasks`, `goals`, `email`). Board already honors it. **Wave-file action at build time:** widen 9.4.1 User Story 3 acceptance from "verify … files gaps" to "implement scroll/highlight in the mapped surfaces" (~+4h).

### Finding 2 — Surface registry must be server-importable  ·  severity: MEDIUM
9.4.1's `engine.ts` (server) imports the tool→surface mapping to emit `open_surface`. 9.1.1 places it in `lib/surfaces/registry.ts` (good — a `lib/` module, not a component) but never guarantees the module is free of `'use client'` / client-only imports.
**Resolution (applied to C2):** `lib/surfaces/registry.ts` MUST be a plain isomorphic module — no `'use client'`, no client-only imports — so both the client `usePanel` controller and server-side `engine.ts` import it. Added as an explicit 9.1.1 acceptance criterion in the contract. The client controller (`panel-provider.tsx`) stays a separate `'use client'` module that *imports* the registry.

### Finding 3 — `chat-pane.tsx` / `composer.tsx` parallel-write conflict  ·  severity: MEDIUM
The epic marks Features 9.3 ∥ 9.4 as parallel. But `chat-pane.tsx` is edited by 9.3.2 (extract `sendChatMessage` controller + focus handle), 9.4.1 (add `open_surface` handling to `applySSEEvent`), and 9.4.2 (proactive card rendering); `composer.tsx` by 9.3.2 and 9.4.2. Run in parallel worktrees these collide.
**Resolution (applied to the ownership summary):** the chat-pane path is **serialized 9.3.2 → 9.4.1 → 9.4.2**. This matches intent — 9.3.2 extracts the single `sendChatMessage` send-path that 9.4.x is meant to reuse. Net effect: 9.3 and 9.4 are **not freely parallel**; treat as 9.3 fully, then 9.4. `/implement-waves` will also catch this via its file-scope isolation check, but it's now explicit so it isn't discovered mid-run.

### Finding 4 — spurious C9 dependency edge  ·  severity: LOW
9.3.1 lists "Blocks 9.4.1 (consumes C9)," and the original C9 consumer list named 9.4.1. But C6 (tool→panel bridge) does not use the command palette; 9.4.1's own dependencies correctly omit 9.3.1.
**Resolution (applied to C9):** removed 9.4.1 from C9's consumer list. 9.4.1 depends only on 9.1.1 (C2) and 9.2.2 (C8). The only thing keeping 9.4.1 after 9.3.2 is the `chat-pane.tsx` serialization (Finding 3), not a contract dependency.

### Finding 5 — `/projects/[id]` alias undocumented  ·  severity: LOW
9.1.3 retains `/projects/[id]` as a `goals`-surface deep-link alias; it wasn't in C5's route table.
**Resolution (applied to C5):** `/projects` and `/projects/[id]` documented as retained `goals`-surface aliases (legacy deep links), alongside the existing `matchPrefixes` behavior in the current nav.

## 5. Low-risk coordination notes (no change required)

- **`source` / `dedupe_key` columns (9.4.2 adds to `conversation_messages`):** proactive rows are legitimate `role='assistant'` messages, so Anthropic-replay readers (`toAnthropicMessages`) handle them correctly with no change; the columns exist only for idempotent dedupe (partial unique index) and UI card rendering. Only nuance: Sentinel memory-extraction may wish to skip `source IS NOT NULL` rows — noted for 9.4.2, not a blocker.
- **Legacy-key precedence (9.1.2):** on store migration, `chat-panel-conversation-id` wins over `chat-tab-active-id`. Reasonable; recorded in C1.
- **308 vs 301 redirects (9.1.3):** Next.js permanent redirects are 308; semantically equivalent to the "301" in C5.
- **Sign-out relocates to rail bottom (9.1.1):** the top bar that held it is deleted; 9.5.1's responsive collapse carries it. Recorded in C3.

## 6. Conclusion

The twelve waves form a clean DAG with a single owner per shared contract and mostly sequential file seams. **One high-severity gap (Finding 1, `focusId` honoring) would cause a silent runtime no-op and must be closed by widening 9.4.1's scope at build time.** The other four findings are pinned in the contracts doc so no wave discovers them mid-implementation. With those reconciliations, Epic 9 is safe to implement in DAG order, starting with Wave 9.1.1.
